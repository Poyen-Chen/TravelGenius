# 推薦引擎現代化規格（歷史候選）

> 本文件保留 2026-09-25 的候選與審查背景，不是目前執行契約。PD-057 已在 App 上架前取消歷史 JSON／Swift 雙軌、遷移選擇及相容資料模型。目前只有 Swift V1 推薦引擎；仍保留的原則只有穩定 catalog ID、唯讀差異預覽與使用者確認後套用。

## 目前有效契約（PD-057）

- packing_items.json 只包含 61 筆正式用品的 ID、名稱與分類。
- seasonal_weather.json、國家與城市 JSON 是事實資料，不是推薦規則語言。
- Swift 根據打包風格、設備、需求、目的地、天氣、活動、青旅及洗衣產生清單。
- UserPreferences 只有打包風格、設備與需求；TripPackingContext 只有目前可選的活動、青旅與洗衣。
- 不載入 packing_rules.json，不判斷 legacy／modern，不顯示版本選擇。
- 更新既有清單仍先產生新增、減量、移除提案，使用者勾選後才寫入。

以下內容只用來追溯原候選，不得作為新增相容程式的依據。

> 歷史候選：本文件保留 2026-09-25 的引擎候選與審查背景。2026-09-26 已完成逐組物品審查；具體目錄、活動／住宿對應及洗衣政策改以 [V1 最小充分物品目錄規格](packing-catalog-v1-spec.md)與 PD-050 為準。引擎安全、快照及人工套用原則未因此失效。

日期：2026-09-25。依 PD-046、PD-047 實作；目前是可測試候選，不代表規則內容已獲接受。

## 目標與非目標

目標是保存舊版推薦引擎中可驗證的計算架構，接到現行 App 的三步建立流程與資料模型，讓團隊能用真實的新輸入測試推薦是否合理。不是恢復舊 UI，也不是直接宣告舊規則正確。

本次不做五國內容研究結論、不發布或同步 PWA、不決定機場層級差異、不自動改寫所有舊行程，也不把工程測試視為人工內容驗收。

## 舊版、改版前現況與目前候選

| 面向 | 原版引擎邏輯 | 現行 App 在本次改動前 | 目前候選 | 還需要檢視什麼 |
| --- | --- | --- | --- | --- |
| 規則骨架 | 依基本、國家／文化、天氣、旅伴、經驗、年齡、性別等層逐條產生，catalog ID 去重並保留原因與排序 | 已有穩定 catalog ID 與舊規則，但新 UI 已不蒐集多個舊輸入，資料與行為脫節 | 保存同一 catalog、順序、去重、數量及理由；現代快照跳過旅伴／經驗／年齡／性別層 | 舊規則內容本身是否合理仍要逐項審查 |
| 個人設定 | 由人口欄位與旅行經驗推測用品 | UI 已改為設備、明確需求、打包風格；舊欄位仍在模型內 | 新行程只用設備、需求、風格；舊欄位只解碼歷史快照 | 設備與需求選項是否足夠 |
| 行程情境 | 沒有可靠的活動、住宿、洗衣結構 | 流程沒有提供，推薦無法判斷這些差異 | 建立第 1 步可覆寫活動、住宿、洗衣；雪地另問賞雪／租借／自備 | 每個情境對應用品是測試規則，須人工評估 |

| 建立流程 | 由舊畫面欄位供應引擎 | 三步流程已優化，但只有部分偏好可用 | 不改三步結構；第 1 步展開本次設定，第 2 步逐項採納推薦 | 欄位順序、文案與預設值由人工操作確認 |

## 資料契約

`UserPreferences` 保留舊人口欄位，目的只有讀取既有 JSON。`devices` 與 `needs` 兩者都有值（包含明確空陣列）時才是新版快照。新全域設定只保存打包風格、設備及需求，並移除舊人口設定鍵。

這裡的 `nil` 是程式資料狀態，意思是舊資料裡「根本沒有這個欄位」，不是使用者明確選擇「什麼都不帶」；明確不選任何設備／需求會保存成空陣列 `[]`。兩者必須分開，否則舊行程可能被誤判成使用者做過新版選擇。

`TripPackingContext` 為版本 1 JSON 快照，包含：

- `activities`：玩水、戶外、雪地、泡湯、運動、正式場合，可複選。
- `stays`：飯店、民宿／公寓、青旅、親友家，可複選。
- `laundry`：未知、會洗、不會洗。
- `snowPlan`：未知、賞雪、當地租、自備；沒有雪地活動時只能是未知。

新行程建立時同時凍結 `packingPreferencesRaw`、`packingContextRaw` 與天氣依據。之後改全域設定不會靜默重算舊行程。非空但解碼失敗的偏好、情境或天氣快照會阻止建議套用，不以空值替代。

## 推薦與檢視流程

新行程推薦依序使用現有 catalog 與規則檔、目的地／月份或天氣、明確設備與需求，再加入活動／住宿／洗衣情境。相同 catalog ID 只保留第一次命中的項目，因此舊規則排序仍影響最後理由；情境項目使用獨立排序區段，不改歷史輸出。

既有清單更新分兩段：

1. `review` 只比較目前清單與新目標，產生新增、數量降低、完整移除三類提案，不改資料。
2. `applyReview` 重新計算並只套用仍然有效且被勾選的提案；成功保存後才採用新版偏好／情境，失敗則恢復數量與快照並保留錯誤。

自訂品永遠不是減量或移除候選。已打包的自動品可出現在候選，但顯示額外警告且預設不勾。先前排除不會被重新新增。

## 目前情境規則（待內容審查）

- 玩水：泳裝、防水袋、快乾毛巾。
- 戶外：戶外鞋、遮陽帽、日用背包、水瓶、雨衣、手電筒、急救包。
- 雪地：保暖帽、防水手套；只有選擇自備時加入雪地裝備總項，避免假設租借或只賞雪也要攜帶器材。
- 泡湯：泡湯毛巾、濕物袋。
- 運動：運動服、運動鞋。
- 正式場合：正式服裝、正式鞋。
- 途中洗衣：加入洗衣用品、洗衣袋；不對每日衣物另設上限，仍依旅程天數與打包風格計算。
- 任一住宿：加入旅行毛巾，但理由要求先確認住宿是否提供；青旅另加置物鎖、耳塞、拖鞋。

這些規則的價值是假設可見、可測、可調，不是目前已證明適合所有旅客。例如飯店通常提供毛巾，所以候選使用「確認後保留」理由而非硬性必帶；洗衣用品也取決於住宿設備與購買便利性。

## 五國內容盤點邊界

現有國家規則不是五國完成度聲明。日本目前有現金／脫鞋／手帕類文化項目；韓國有交通卡且舊胃藥推測在新版被排除；香港、美國、越南尚沒有等量的國家內容。後續研究必須逐項留下來源、適用條件、是否影響打包、風險與建議文案，再由使用者決定是否進 catalog／規則。不能用常識補齊或因缺少規則就聲稱不需要特別用品。

## 驗證與人工檢視

自動驗證至少包括：7,200 組舊快照輸出完全一致、192 組新版設備／需求／風格、情境規則、洗衣數量、雙向提案、客製與已打包保護、排除、損毀快照、SwiftData 升級及重開。

人工檢視重點：

1. 建立流程的設定是否容易理解，預設是否合理。
2. 用五個國家、不同天數與天氣，逐項判斷「為什麼出現／為什麼沒出現」。
3. 舊行程的兩種選擇及增／減／移除是否看得懂。
4. 驗證 `fullOnly`、活動、住宿、洗衣清單的實際推薦結果；目前方向已接受，但仍可依測試結果調整內容。
5. 已打包品維持「警告後可選」，並確認警告在實際操作時足夠清楚。

通過以上檢視前，不建立 acceptance tag，也不把本文件的候選規則寫成已核准產品規格。

## 已辨識但本次不恢復的舊程式產物

- `TripType` 是資料模型中的觀光、商務、背包、家庭欄位；現行建立流程固定保存觀光，本推薦引擎沒有讀取它，因此本次不拿它暗中推測用品。正式場合改由使用者明確選活動。
- `TripFormView` 是舊的新增／編輯表單，仍包含出發國家與城市選擇；目前沒有程式入口引用它。`OnboardingTripSetupView` 也保留舊的同行／經驗文案與出發城市 UI，但目前沒有程式入口引用。它們沒有被接回現行流程，也未在本次直接刪除，避免把「移植推薦架構」擴張成未審核的舊碼清除。
- 正式使用中的新建行程流程固定 `originCountryCode = TW` 且 `originCity` 留空。示範資料仍可明確寫台北，因為那代表該筆示範行程，不是全域預設。
