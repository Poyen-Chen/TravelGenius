# Packmon iOS 分階段整合與人工驗收計畫

更新：2026-09-24。狀態：第 0～3 階段已人工驗收；第 4 階段已有候選、待人工驗收（PD-033～035）。目前啟用 Open-Meteo，WeatherKit 保留未啟用。目前有效規格見 [技術規格索引](implementation-specifications.md)；下一階段見 [天氣技術規格](weather-integration-spec.md)。下方歷史交付文字保留當時狀態，以驗收表及最新決策為準。

## 目標與範圍

- iOS 為主產品；PWA 僅作為已採納功能的參考與測試入口，不全面移植。
- 初期目的地：日本、韓國、香港、美國、越南；先選國家／地區，再選其城市（PD-021）。台灣出發／回程參考資料保留。
- 吸收 TravelGenius 的物品目錄、穩定 ID、情境規則、行程快照與合併保護概念。
- 將已確認的天氣、個人設定方向帶回 App；詳細情境與數量政策須先完成該階段規格確認。
- 提供可重複使用固定素材的圖片清單（PD-019），維持 Structure C 與 PackmonTheme。
- 不包含 3D、跨端資料同步／轉移、雲端帳號、每次 AI 生圖、遠端資料熱更新或自動偏好學習。PWA 適用部分依 PD-029～031 選擇性對齊，不全面移植或自動部署。

這份計畫不是對前述討論提案的整批核准。以下在相依階段前處理，不阻擋獨立的早期階段：

## 每一階段的固定流程

1. 從上一個「已人工驗收」的 commit 建立下一階段分支；只實作當階段範圍。
2. 完成相應建置與測試，產生可操作的候選版本。測試資料只在指定測試容器使用，不自動植入一般安裝。
3. 提交候選版本並 push 階段分支，記錄 SHA、測試結果、畫面證據及操作步驟。候選提交不代表已驗收。
4. 暫停，讓使用者人工操作。只有明確表示該階段通過，才能往下一階段。
5. 有問題就在同一階段修正並追加提交，重新驗收受影響案例；不把問題帶入下一階段。
6. 通過後，將精確的功能 commit SHA、使用者核准日期及結論寫入驗收紀錄，以獨立文件提交保存。先 commit 並 push 驗收紀錄，再建立 annotated tag `packmon-ios-stage-XX-accepted` 指向該驗收提交並 push；確認分支與 tag 均已在遠端保存後，才從該 tag 建立下一階段分支。已發布的驗收 tag 不移動、不覆寫。

每次交付結尾都列出：本階段完成／未包含項目、工程檢查及限制、人工操作路徑與預期結果、候選分支／SHA。工程通過不代替人工核准。

不自動合併 main、不 force-push、不改写已分享的提交。每次開始或交接前都讀取下方驗收表，不能只憑分支名稱推定通過。

## 回退方式

- 尚未驗收：保留候選分支與問題紀錄，回上一個已驗收版本比較；未提交的修改先妥善保存，不能直接丟棄。
- 已 push 的錯誤修改：用明確範圍的 revert 提交保留歷史；不以 reset --hard 或 force-push 覆蓋共同歷史。
- 檢查舊版本：優先從已驗收 SHA 建立獨立工作目錄及測試安裝，避免破壞當前工作。
- 資料模型有變更：修改前保存測試資料複本並驗證恢復；Git 回退只還原程式，不會還原 SwiftData 或 UserDefaults。不要讓舊版程式直接打開已遷移的唯一資料副本。
- 候選版須記錄 commit SHA、App build、測試容器／裝置與資料版本，避免使用者測到另一個版本。
