# 個人化打包設計（提案）

日期：2026-10-19。狀態：**設計提案**。M1～M4 尚未授權實作；視覺呈現的概念 1、2 已選定並記錄為 PD-061。

## 目標

讓清單從「依行程推薦」進一步變成「依**這個人**推薦」：同一趟東京五天，怕冷、只帶登機箱、每次襪子都不夠的人，應該拿到和別人不一樣的清單。而且 App 要能從每趟旅行中學到這些差異，但不能在使用者不知情時改清單。

## 現況盤點

| 層級 | 已有的個人化輸入 | 生效方式 |
|---|---|---|
| 全域偏好 | 打包風格（輕便／一般／完整）、6 種設備、3 種需求 | 建立行程時凍結成快照（PD-028） |
| 常備用品 | 名稱／分類／數量／重量，打包頁可加星號存成常備 | 建立時複製進行程；同名推薦讓位（PD-028、PD-031） |
| 每趟情境 | 8 種活動、青旅、洗衣、天氣快照、目的地、天數 | 標籤 → `packing_rules.json`（PD-060） |
| 每趟修正 | 排除項目、自訂項目、行程編輯後的增減 review | 只在該趟生效；既有清單只透過勾選 review 改動（PD-041、PD-058） |

**缺口：**
1. **不會學習**：`PackingLibraryItem.useCount` 和 `recordUsage` 已經存在但沒有被呼叫；「我的 → 歷史回顧」只是佔位入口。
2. **沒有跨行程的個人規則**：「我從來不帶睡衣」或「襪子每次要多一雙」，每趟都得手動排除或修改。
3. **天氣門檻是固定的**：`hot ≥ 30°C`、`cold ≤ 10°C`，不管使用者是怕冷還是怕熱。
4. **不知道行李限制**：只帶登機箱和有託運，在液體、數量上的需求差很多。

## 設計原則（不可違反）

沿用既有決策，新功能也必須遵守：

1. **單一推薦路徑**：個人化只是在現有引擎的前後各加一層。沒有個人資料時，輸出必須和現在完全相同，2,916 組 oracle 與 540 組矩陣不得變動。
2. **全域設定不改舊行程**：個人規則和體感設定和偏好一樣，建立時凍結成快照（PD-028）。
3. **學習只產生提案**：回顧結果不會自動變成規則，必須由使用者確認（延續 PD-028「不自動學習」的精神，並把它升級成「學習但需確認」）。
4. **既有清單只透過 review 改動**：新增、增量預設勾選；減量、移除預設不勾；自訂項目受保護（PD-041、PD-058）。
5. **不從人口特徵推測**，只用使用者明確給的輸入或明確回顧（PD-031）。
6. **資料留在本機**，不需要帳號、不使用雲端 AI。個人規則和常備用品放在同一個個人庫，之後可以跟著 PD-060 的 CloudKit 一起選擇性同步。

## 四個模組

### M1 我的打包規則（跨行程的個人規則）

使用者對某個目錄用品設定長期規則：

| 規則 | 效果 | 範例 |
|---|---|---|
| 不再建議 | 推薦結果移除該項 | 「我不帶睡衣」 |
| 數量 ±N（−3～+3） | 推薦數量加減後限制在 1～99 | 「襪子 +1」 |
| 一律帶 | 沿用既有**常備用品**，不另做新機制 | 「眼罩」 |

- **入口**：
  - 打包頁長按用品，選單出現「以後都不要建議」「以後多帶 1 個」。確認頁會寫明「只影響之後新建的行程」。
  - 「我的 → 我的打包習慣」：列出全部規則，可修改、刪除。
- **保護清單**：護照、信用卡／金融卡、手機不能設為「不再建議」，只能調整數量。
- **原因標示**：受規則影響的項目，原因後面加「・依你的習慣 +1」；被排除的項目在 review 和建立流程中可以展開查看，不會無聲消失。
- **每趟可關閉**：建立流程第 1 步的每趟覆寫區顯示「已套用 3 條個人規則」，可以只對這趟關閉某條規則。

### M2 行後回顧與學習提案

- **時機**：行程標記完成（`Trip.complete`）後，總覽頁出現「花 1 分鐘回顧這趟」卡片。可以跳過，跳過後不再催促。
- **流程（3 步）**：
  1. **快速標記**：清單依分類列出，每項預設「有用到」，點一下依序切換成「沒用到」「不夠用」。只需要改例外的項目。
  2. **少帶了什麼**：從 61 項目錄搜尋，或輸入自訂名稱。
  3. **小結**：顯示完成度，以及「下次可以這樣調整」的提案；勾選後才寫入規則或常備用品。
- **提案規則**（確定性、可解釋）：只看最近 5 次有回顧、而且該項有被推薦的行程。

| 證據 | 提案 |
|---|---|
| 「沒用到」≥ 2 次，且「沒用到」≥「有用到」的 2 倍 | 數量型用品：−1；其他用品：不再建議（保護清單除外） |
| 「不夠用」≥ 2 次 | +1 |
| 目錄用品被回報「少帶」≥ 1 次 | 加入常備用品 |
| 自訂名稱被回報「少帶」≥ 1 次 | 加入常備用品（使用自訂名稱） |

- 每個提案都附證據，例如「最近 3 趟有 2 趟沒用到」。拒絕的提案要等出現新證據才會再出現。
- **歷史回顧頁**：取代目前的佔位入口，列出每趟行程的打包完成度、回顧狀態，以及當時少帶的東西。

### M3 體感設定

- 在「我的 → 我的打包習慣」新增三選一：**怕冷／一般／怕熱**（預設一般，所以現有輸出不變）。
- **天氣預報門檻**：
  - 怕冷：`cold` 門檻從 ≤ 10°C 放寬到 ≤ 15°C。
  - 怕熱：`hot` 門檻從 ≥ 30°C 放寬到 ≥ 27°C。
- **季節參考**：月份資料沒有溫度數值，所以改輸出 `comfort:cold`／`comfort:heat` 標籤，由 JSON 規則決定要加哪些用品（例如怕冷時，溫和月份也加薄外套）。
- **內容需要審核**：哪些用品對體感有反應，要另做一次內容審核（PD-049 的最小充分原則），不能只靠這份工程設計決定。

### M4 行李限制（每趟）

- 建立流程第 1 步新增一個選項：**只帶登機箱／有託運行李／還不確定**。
- 會改變的內容：
  - 只帶登機箱時加 `luggage:carry-on` 標籤，輕便風格的衣物上限優先。
  - 「能帶嗎」查詢會提示液體 100ml 規則。
- **需要決策**：目錄目前沒有「透明夾鏈袋／分裝瓶」。新增目錄項目必須另外決策並出新版 App（目錄身分屬於 App 版本契約），所以 M4 排在最後。

## 資料模型

| 新增 | 位置 | 說明 |
|---|---|---|
| `PersonalPackingRule` | 個人庫 SwiftData store（與 `PackingLibraryItem` 同一個 schema） | `catalogItemID`、`kind`（exclude／quantityDelta）、`delta`、`source`（manual／retrospective）、`createdAt` |
| `ComfortProfile` | `UserPreferences` 加一個欄位 | 解碼舊資料時缺少此欄位視為 `.neutral` |
| `Trip.personalRulesRaw` | Trip | 建立時凍結的規則快照（JSON，帶版本）；空字串代表沒有規則，維持現況 |
| `Trip.luggagePlan` | `TripPackingContext` 加一個欄位 | 預設 `.unknown`，不產生標籤 |
| `Trip.retrospectiveRaw` | Trip | `{version, completedAt, items: {catalogID或名稱: used/unused/short}, forgotten: [...]}` |

快照損毀時的處理和現有偏好快照一樣：阻擋變更，不靜默改用全域設定。

## 引擎接點

```
UserPreferences(+comfort) ─┐
TripPackingContext(+luggage)┼─► tags ─► PackingRuleEngine.generate ─► PersonalRuleLayer.apply ─► 建立清單／review
天氣（門檻依 comfort）──────┘                                          ▲
                                                Trip.personalRulesRaw（快照）
```

- `PackingListGenerator.generate` 增加 `comfort:` 和 `luggage:` 標籤，只在非預設值時加入，確保現有 oracle 不變。
- `PackingWeather.tags(comfort:)` 接收體感參數，調整門檻。
- `PersonalRuleLayer` 是純函數：輸入 `[GeneratedItem]` 和規則快照，輸出調整後的清單，以及被排除項目的說明。`review(for:)` 走同一條路徑，所以行程編輯和 review 也會反映個人規則。
- 常備用品優先於個人規則：同一個用品若同時是常備用品，以常備用品的數量為準。

## 驗收條件

**自動測試**
- 沒有規則、體感為一般、行李未定時，2,916 組 oracle 和 540 組矩陣完全相同。
- 規則：排除、數量加減與 1～99 的上下限、保護清單、常備用品優先、每趟關閉、快照損毀時阻擋。
- 修改全域規則後，既有行程的清單和 review 結果都不變。
- 回顧提案：門檻剛好達到／差一次、拒絕後要有新證據才再出現、保護清單不產生排除提案。
- 天氣門檻：在 10／15／27／30°C 邊界上，各體感設定的標籤正確。

**人工驗收**
1. 在東京行程把襪子設為「以後多帶 1 個」。原行程不變；新建一趟行程，襪子多 1，原因顯示「依你的習慣 +1」。
2. 完成兩趟回顧，都把睡衣標「沒用到」。小結出現「不再建議睡衣」並附證據；勾選後，下一趟不再出現睡衣，展開可以看到被排除的原因。
3. 設為怕冷，建立 14°C 的預報行程，出現保暖類用品；改回一般後新建同樣行程則不出現。

## App／PWA 評估

規則層和回顧都是與平台無關的資料，適合之後同步到 PWA，但 PWA 使用名稱身分的引擎（PD-041），需要另外對應。本提案只涵蓋 iOS；要同步到 PWA 須另行決定範圍。

## 待使用者決定

1. **學習方式**：只出提案、由使用者確認（建議），或是達到門檻就自動套用？
2. **實作順序**：建議 M1 → M2 → M3 → M4。M1 最小、價值最直接；M2 依賴 M1 的規則格式；M4 依賴目錄決策。
3. **保護清單**：護照、信用卡、手機這三項是否足夠？
4. **回顧預設狀態**：每項預設「有用到」（快，建議），或預設「未標記」（較準，但較累）？
5. **體感**：三段選擇（建議），或讓使用者直接設定溫度門檻？
