# 第 2 階段：打包目錄與規則契約

> 歷史契約：本文件記錄階段 2 的 JSON 規則與相容機制，不是目前 iOS 執行契約。PD-057 已在上架前取消雙軌；目前以 [V1 最小充分物品目錄規格](packing-catalog-v1-spec.md)的 61 項目錄及單一 Swift 推薦引擎為準。

## 範圍

採納 TravelGenius 的「目錄只定義一次、規則以固定 ID 引用、舊清單原地合併」概念，保留 Packmon 現有推薦政策。不移植 CloudKit、CDN 更新、行李庫、重量估算、需求替代品解析或個人設定快照；後者依分階段計畫另行處理。

## 隨 App 發布的資料

- 階段 2 驗收時的 `packing_items.json` 為 `version: 1`、38 種物品；後續雙軌候選曾擴充為 95 筆定義並以 61 個 `activeItemIDs` 限制新版推薦。這段相容設計已由 PD-057 取代；現行目錄直接收斂為 61 筆正式定義，不保留 active set 或 legacy aliases。
- `packing_rules.json` 曾在階段 2 作為執行時規則來源：每條規則有固定 `id`、`layer`、`match`、`reasonZh`、`items`，並以 `itemId` 引用目錄。PD-057 已將現行推薦條件與數量政策收斂到單一 Swift 引擎，該檔案不再隨現行 App 載入。
- `PackingCatalog.validate` 拒絕未知版本、重複物品／規則 ID、跨物品名稱別名衝突、不存在的引用、非正數數量及 perDay 同時指定固定數量。分類由 Codable enum 驗證。無遠端輸入，壞的隨附資料直接報錯，不以空推薦進行刪除合併。
- 本階段保留既有 match 執行器，不引入全新 tag/need 語言；同一條件下推薦名稱、分類、數量、理由、排序與第 1 階段一致。保留既有月份備援，區域氣候問題留第 4 階段。

## 識別與升級

- `PackingItem.id` 仍是每個行程物品的 UUID；新增可空的 `catalogItemID` 表示目錄身份。兩者用途不同。
- 舊自動物品在 sync 時用精確名稱／已列出的別名補 ID，保留原 UUID、名稱、數量、分類、理由、勾選。自訂物品不改成系統物品；同名自訂用品仍可抑制重複推薦。
- 原插座轉接頭名稱含 Type 字串，集中對應 `plug-adapter`。新行程仍顯示當地插座型號；既有清單項目保留當時名稱，修改目的地後的內容更新 UX 不在此階段重做。
- `Trip.excludedPackingIDsRaw` 儲存排除 ID，同時保留 `excludedPackingNamesRaw`。舊名稱排除在 sync 轉成 ID；新版刪除同時記錄 ID 及名稱，因此改標籤不會使刪除過的物品重新出現。
- 未知舊物品／未知 ID 保留，不因目錄缺少對照而刪除。已打包、自訂永不自動刪除；其餘已知且不再適用的自動物品仍沿用舊版移除政策。相同身份的既有物品不覆寫數量。
- 新增兩個具預設／可空值的欄位，使用 SwiftData additive migration；不刪除舊欄位、不啟用新同步服務。不承諾舊 App 能開啟升級後唯一資料庫，回退前需保存升級前資料副本。

## 可重跑驗證

執行 `bash scripts/test_packing_regression.sh`（macOS + Xcode）。腳本從 `packmon-ios-stage-01-accepted` 匯出原始碼，不切換或修改工作分支，並以同一套 fixture 編譯原版及候選版真實模型／引擎。

1. 7,200 組條件：五國、12 個月、1/5/12 天、兩種打包風格、五種同行方式，以及無預報／空預報／炎熱有雨／寒冷溫和；輪替年龄、性別、經驗。逐筆比對名稱、分類、數量、理由、排序，不能只比項目數。
2. 原版 executable 建立真實 SwiftData 磁碟資料庫，再複製到獨立資料夾供新版升級。包含已打包項目、手調 99 件、自訂同名物品、舊名稱排除、未知物品與過季項目。
3. 檢查 UUID／數量／勾選／自訂保留、舊排除轉換、已知過季項目移除、未知物品保留、連跑不重複、改名稱不重複、用 ID 排除。
4. 存檔後退出，另一個新程序重開確認持久化。保留原始 fixture 與候選副本於輸出的暫存路徑，不操作使用者資料。

這是 macOS SwiftData／引擎回歸測試，不取代 iOS Simulator 建置、實際安裝啟動或人工驗收。未包含 iCloud、實機、所有 OS 版本、跨時區或所有規則組合的證明。
